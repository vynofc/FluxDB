## Kritische Bugs (Crash / Datenverlust / Race Conditions)

### #1 — Race Condition: `DatabaseService` wird während laufendem Index disposed
**Datei:** `WPF/FluxDB/Views/MainWindow.xaml.cs:107-141`, `:1529`, `WPF/FluxDB/Services/DatabaseService.cs:440-445`

`InitializeDatabaseForFolder()` ruft `_databaseService?.Dispose()` auf. Gleichzeitig kann `IndexerService.ScanFolderAsync` noch laufen (z. B. von einem früheren Ordner-Wechsel oder weil `ShowRefreshDialog` bei `Choice.Entire` `InitializeDatabaseForFolder` aufruft **ohne** `_isIndexing` zu prüfen oder zu cancellen). Danach wird auf die geschlossene Connection zugegriffen → `ObjectDisposedException` oder `SQLiteException` mitten im Scan. Umgekehrt: `StartIndexing` benutzt `_indexerService`, das gerade ersetzt wurde, wenn der Nutzer während des Scans einen anderen Ordner öffnet.

**Fix:** In `InitializeDatabaseForFolder` zuerst `_indexCancellation?.Cancel()` + auf `_isIndexing == false` warten, dann dispose. Oder ein Generation-Token: nach dem Dispose nie mehr das alte Service benutzen.

### #2 — `LoggingService.Shutdown()` disposed den Writer, aber `Log()` läuft weiter
**Datei:** `WPF/FluxDB/Services/LoggingService.cs:158-166`, `:40-47`, `WPF/FluxDB/Views/MainWindow.xaml.cs:2028-2040`

`Shutdown()` setzt `_logWriter = null` und disposed ihn. Falls nach `Shutdown()` noch `Log()` aufgerufen wird (z. B. aus dem Hintergrund-Update-Task in `SplashWindow_Loaded`, der per `Task.Run` weiterläuft und `Application.Current.Shutdown()` asynchron aufruft), wird in `GetWriter()` ein neuer `StreamWriter` erstellt, der nie disposed wird. Zusätzlich: `ProcessWriteQueue` kann noch in der Warteschlange sein und greift dann auf den halb-disposeden Zustand zu. Auch `Shutdown()` greift auf `_logWriter` unter `_lock` zu, während `ProcessWriteQueue` ihn unter `_writerLock` schreibt — zwei verschiedene Locks → **echte Race Condition** zwischen Flush/Dispose und Write.

**Fix:** `Shutdown()` sollte zuerst `_isProcessingQueue = false` setzen, die Queue leeren, dann unter `_writerLock` den Writer disposen, und ein `_shutdown` Flag einführen, das `Log()` und `GetWriter()` prüfen.

### #3 — `UpdateFolderPath` SQL aktualisiert den Root-Pfad falsch
**Datei:** `WPF/FluxDB/Services/DatabaseService.cs:322-345`

```sql
UPDATE files SET path = @newPrefix || SUBSTR(path, @oldLen + 1), ...
```

Wenn `path == @oldPath` (der Ordner selbst), dann ist `path.Length == oldLen - 1` (ohne Trailing-`\`), und `SUBSTR(path, oldLen + 1)` ergibt `""`. Resultat: `newPrefix || ""` = `"C:\neuer\pfad\"` — mit fälschlichem Trailing-Backslash. Der Root-Eintrag bekommt also einen anderen Pfad als der echte (`newPath` ohne `\` am Ende). Beim nächsten `GetFilesInFolder`/`SearchFiles` mit `path LIKE 'prefix%'` passt es zwar, aber `existingPaths.Contains(path)` in `MarkDeletedFiles` schlägt fehl → der umbenannte Ordner-Eintrag wird fälschlich als `deleted=1` markiert (falls Ordner in `files` indiziert sind — aktuell nur Dateien, aber die Inkonsistenz bleibt).

**Fix:** `SUBSTR(path, @oldLen + 1)` nur anwenden wenn `path LIKE @oldPrefix`; für `path = @oldPath` direkt `@newPath` setzen:
```sql
UPDATE files SET path = CASE WHEN path = @oldPath THEN @newPath ELSE @newPrefix || SUBSTR(path, @oldLen + 1) END, ...
```

### #4 — WebView2 `Navigate(file.Path)` mit unescaped Pfad / kein `file://` URI
**Datei:** `WPF/FluxDB/Views/MainWindow.xaml.cs:701-715`

`webPdfPreview.CoreWebView2.Navigate(file.Path)` übergibt einen rohen Windows-Pfad (`C:\...\file.pdf`) statt einer URI (`file:///C:/...`). WebView2 behandelt das je nach Zeichen (Leerzeichen, `#`, `%`, Unicode) als ungültige URL oder interpretiert `#` als Fragment → PDF lädt nicht oder bricht. Außerdem fehlt jede Prüfung, ob `CoreWebView2` überhaupt initialisiert ist (`EnsureCoreWebView2Async` kann `null` liefern, wenn WebView2 Runtime fehlt).

**Fix:** `Navigate(new Uri(file.Path).AbsoluteUri)` oder explizit `"file:///" + file.Path.Replace('\\','/')`. Fehlerfall `WebView2RuntimeNotFoundException` separat abfangen und Hinweis zeigen.

### #5 — `App.xaml` StartupUri + manuelle MainWindow-Erstellung = potenziell zwei MainWindow-Instanzen / falsches Shutdown-Verhalten
**Datei:** `WPF/FluxDB/App.xaml:6`, `WPF/FluxDB/Views/SplashWindow.xaml.cs:72-116`

`SplashWindow_Loaded` erstellt `new MainWindow()`, setzt `ShutdownMode = OnExplicitShutdown`, ruft `main.Show()`, dann `Hide(); Close();` auf sich selbst. Danach `Application.Current.MainWindow = main` und `ShutdownMode = OnMainWindowClose`. Probleme:
1. Wenn der Update-Check `return false` liefert, wird `Application.Current.Shutdown()` aufgerufen, während `main` läuft — das ist OK. Aber das Splash-`Close()` passiert **vor** `ShutdownMode`-Umstellung: In dem Moment gibt es kein geöffnetes Fenster (main ist noch nicht `Shown` wenn `Hide()`+`Close()` synchron abgearbeitet werden) — WPF könnte die App beenden, bevor `main` erscheint (je nach Timing, da `Show()` vorher aufgerufen wurde, geht es meist gut, aber es ist fragil).
2. `btnCancel` im Splash ruft `Application.Current.Shutdown()` — wenn das vor `main.Show()` passiert, ok. Danach würde es die ganze App killen, obwohl main schon offen ist — der Cancel-Button wird aber nie deaktiviert/versteckt.

**Fix:** Reihenfolge `main.Show()` → `Application.Current.MainWindow = main` → `ShutdownMode = OnMainWindowClose` → `this.Close()`. Cancel-Button nach Main-Show deaktivieren.

## Schwerwiegende Bugs (falsches Verhalten)

### #6 — Suche ignoriert `_currentViewFolder` vs. `_currentRootFolder` Inkonsistenz + falsches SQL (HAVING statt WHERE)
**Datei:** `WPF/FluxDB/Services/DatabaseService.cs:347-385`

```sql
WHERE f.deleted=0 AND f.path LIKE @folderPrefix
GROUP BY f.id
HAVING f.name LIKE @q OR f.path LIKE @q OR n.note LIKE @q
   OR EXISTS (...)
```

Das `HAVING` auf nicht-aggregierten Spalten (`f.name`, `f.path`, `n.note`) funktioniert in SQLite zwar (bare columns erlaubt), ist aber semantisch falsch und langsam — die Filterung sollte in `WHERE` geschehen (vor dem GROUP BY). Mit `WHERE` statt `HAVING` wäre der Index `idx_files_name` nutzbar. Zusätzlich: `LIKE` mit `%query%` ist ohnehin nicht index-tauglich, aber zumindest semantisch korrekt wäre es.

### #7 — `GetDirectoriesWithTaggedFiles`: falsches Präfix-Handling, `Substring` Crash-Gefahr
**Datei:** `WPF/FluxDB/Services/DatabaseService.cs:387-416`

`fullPath.Substring(prefix.Length)` — wenn `fullPath` kürzer ist als `prefix` (sollte nicht vorkommen wegen `LIKE @folderPrefix`, aber `LIKE` matched case-insensitiv je nach Collation und das Prefix könnte unterschiedlich normalisiert sein), wirft `Substring` eine `ArgumentOutOfRangeException`. SQLite `LIKE` ist standardmäßig case-insensitive für ASCII, C# `Substring` arbeitet mit der C#-Länge — bei abweichender Groß/Kleinschreibung ist die Länge zwar gleich, aber wenn `@folderPrefix` durch Pfad-Normalisierung (`Path.GetFullPath`) anders aussieht als der gespeicherte Pfad, kann es krachen. Robuster: `fullPath.Length >= prefix.Length` prüfen.

### #8 — `PerformSearch` zeigt `results.Count` statt gefilterte Anzahl
**Datei:** `WPF/FluxDB/Views/MainWindow.xaml.cs:1179`

```csharp
txtFileCount.Text = $"{results.Count} found";
```
`results` ist die ungefilterte Liste; die Anzeige im Grid ist zusätzlich um Hidden-Files und Filter reduziert. Der Counter stimmt nicht mit dem sichtbaren Ergebnis überein. Sollte die gefilterte Liste zählen.

### #9 — Copy/Move: `_clipboardIsCut` wird bei Paste aus System-Clipboard nicht zurückgesetzt
**Datei:** `WPF/FluxDB/Views/MainWindow.xaml.cs:339-367`

Wenn der Nutzer Dateien im Windows-Explorer mit Strg+X ausschneidet und in FluxDB einfügt, liest `PasteFiles` die System-Clipboard-FileDropList — `_clipboardIsCut` ist dabei `false` (weil es nicht über FluxDB `CopySelectedFiles(true)` gesetzt wurde). Die Dateien werden also **kopiert statt verschoben**, obwohl der Nutzer "Ausschneiden" gewählt hat. Umgekehrt bleibt `_clipboardIsCut = true` aus einer früheren FluxDB-Cut-Operation bestehen, wenn der Nutzer danach im Explorer normale Dateien kopiert → diese werden **fälschlich verschoben** (Datenverlust-Gefahr am Quellort!). Windows markiert Cut im Clipboard über das `Preferred DropEffect`-Flag, das hier nie gelesen wird.

**Fix:** `Clipboard.GetData(DataFormats.FileDrop)` + `Preferred DropEffect` auslesen, oder nur den internen `_clipboardFiles`/`_clipboardIsCut` Zustand benutzen und den System-Clipboard als reinen Copy behandeln.

### #10 — `CopyOrMoveFilesAsync` verschiebt Ordner nicht korrekt bei "move"
**Datei:** `WPF/FluxDB/Views/MainWindow.xaml.cs:1869-1891`

Bei Ordnern wird `CopyDirectoryRecursive(src, dest)` + `Directory.Delete(src, true)` ausgeführt statt `Directory.Move` (was auf demselben Volume ein atomarer Rename wäre). Neben Performance-Verlust schlägt das bei großen Bäumen fehl, wenn einzelne Dateien gesperrt sind — dann ist der Ordner halb kopiert und die Quelle teilweise gelöscht. Außerdem wird `UpdateFolderPath(src, dest)` nur bei Ordnern aufgerufen — die `.fluxdb`-Datei im verschobenen Ordner wird mitkopiert/gelöscht, aber der DB-Pfad des Ziels zeigt auf den neuen Ordner, der nun eine `.fluxdb` enthält — die DB des **Ziel-Roots** wird aber nicht aktualisiert.

### #11 — Rename-Dialog: ungültige Zeichen / Extension-Verlust bei mehrfacher Extension
**Datei:** `WPF/FluxDB/Views/MainWindow.xaml.cs:423-468`

`Path.GetFileNameWithoutExtension("archive.tar.gz")` → `"archive.tar"`, Extension `".gz"` → Rename zu `"neu.tar.gz"` ok. Aber wenn der Nutzer im Dialog `"neu.tar.gz"` eintippt, wird `"neu.tar.gz.gz"`. Es gibt keine Validierung auf ungültige Dateinamen-Zeichen (`\ / : * ? " < > |`) — `File.Move` wirft dann eine Exception, die zwar abgefangen wird, aber erst nach dem fehlgeschlagenen OS-Call. Zusätzlich: Rename eines Ordners, der gerade in `_backHistory`/`_forwardHistory`/Breadcrumbs referenziert ist, führt zu toten Einträgen (Navigation in nicht-existente Ordner schlägt dann still fehl, da `NavigateToFolder` bei nicht-existierendem Pfad einfach returned).

### #12 — `Window_PreviewKeyDown`: Enter öffnet auch beim Tippen in ComboBox/Buttons
**Datei:** `WPF/FluxDB/Views/MainWindow.xaml.cs:220-317`

Nur `e.OriginalSource is TextBox` wird ausgenommen. Wenn der Fokus auf `cmbFilter` liegt und der Nutzer Enter drückt, um die Auswahl zu bestätigen, wird stattdessen `OpenSelectedItem()` aufgerufen. ## Mittelschwere Bugs

### #21 — `MarkDeletedFiles` mit Scope-Prüfung: Root-Pfad selbst nie "existing"
**Datei:** `WPF/FluxDB/Services/DatabaseService.cs:249-287`

`scopePath.StartsWith(scopePath + "\\")` — für eine Datei direkt im Scope-Root ok. Aber `existingPaths` wird in `IndexerService` nur mit Dateien gefüllt (Ordner werden nie indexiert). Falls zukünftig Ordner in `files` landen, würden alle Ordner-Einträge als deleted markiert. Aktuell harmlos, aber fragil. Zudem: `MarkDeletedFiles` liest **alle** nicht-gelöschten Dateien und filtert in C# statt im SQL (`WHERE path LIKE @scope`) — Performance bei großen DBs.

### #22 — `GetFilesInFolder` liefert rekursiv alle Dateien; Filterung auf direkte Kinder passiert im UI-Thread-LINQ
**Datei:** `WPF/FluxDB/Views/MainWindow.xaml.cs:1804-1814`

`GetFilesInFolder(currentFolder)` lädt **alle** Dateien unterhalb (rekursiv) aus der DB in den Speicher und filtert dann mit `Path.GetDirectoryName(f.Path) == currentFolder` — bei 100k Dateien im Baum werden alle geladen, nur um 50 anzuzeigen. Massiver Speicher-/Performance-Bug bei großen Roots. Die DB-Query sollte direkt filtern: `WHERE path LIKE @prefix AND path NOT LIKE @prefix || '%\%' ESCAPE...` bzw. mit `SUBSTR`.

### #23 — String-Vergleich `Path.GetDirectoryName(f.Path) == currentFolder` case-sensitiv
**Datei:** `WPF/FluxDB/Views/MainWindow.xaml.cs:1806`, `WPF/FluxDB/ViewModels/MainViewModel.cs:309`

Windows-Pfade sind case-insensitiv. Wenn die DB `C:\Foo\bar.txt` speichert und `currentFolder` `c:\Foo` ist (z. B. aus Breadcrumb), matcht nichts → Ordner wirkt leer. `StringComparison.OrdinalIgnoreCase` fehlt.

### #24 — Tag-Autocomplete-Popup wird nie befüllt/geöffnet
**Datei:** `WPF/FluxDB/Views/MainWindow.xaml.cs:1343-1404`

Es gibt Handler für `tagAutocompleteList` und `tagAutocompletePopup`, aber **kein** `TextChanged`-Handler auf `txtTagInput`, der die Liste mit vorhandenen Tags aus der DB füllt und `tagAutocompletePopup.IsOpen = true` setzt. Die Autocomplete-Funktion ist tot (UI vorhanden, Logik fehlt). Zusätzlich fehlt eine `GetAllTags()`-Methode im `DatabaseService` komplett.

### #25 — `AutoSaveTags` speichert Note bei jedem Tag-Remove mit
**Datei:** `WPF/FluxDB/Views/MainWindow.xaml.cs:1324-1341`

Entfernen eines Tag-Chips speichert auch den aktuellen `txtNotes.Text` — ohne dass der Nutzer "Save" gedrückt hat. Ungespeicherte Notiz-Änderungen werden so unbeabsichtigt persistiert. Umgekehrt werden Note-Änderungen ohne Save verloren, wenn der Nutzer danach die Datei wechselt — inkonsistentes Save-Modell (Tags auto, Notes manuell, aber Tag-Aktion speichert Notes mit).

Alle selektierten `FileEntry`-Objekte teilen sich danach **dieselbe** `List<string>`-Instanz (`tags`). Spätere Mutation an einem Eintrag würde alle betreffen. Kopie nötig: `file.Tags = new List<string>(tags)`.

### #27 — Preview: `_previewVersion` Check fehlt im Text-Pfad; PDF-Navigation nicht gecancelt
**Datei:** `WPF/FluxDB/Views/MainWindow.xaml.cs:716-774`

Im Text-Branch wird `_previewVersion != version` geprüft — gut. Aber: `webPdfPreview.CoreWebView2.Navigate(file.Path)` wird nie gecancelt; bei schnellem Wechsel zwischen zwei PDFs gewinnt die letzte Navigation, was ok ist, aber `EnsureCoreWebView2Async()` ohne Cancellation kann bei langsamem Init die alte Datei anzeigen. Zudem Race: `UpdatePreview(null)` navigert `about:blank` während `EnsureCoreWebView2Async` noch läuft → `CoreWebView2` könnte danach null sein.

### #28 — `SettingsService.Save`/`Load` nicht thread-sicher
**Datei:** `WPF/FluxDB/Services/SettingsService.cs:79-111`

`Save` wird aus UI (Filter-Wechsel, Sort, Navigation) und potenziell parallel aus `LoggingService.GetMaxBufferLines` → `GetDevSettingInt` → `Load()` gerufen (Logging kommt aus beliebigen Threads!). `File.ReadAllText`/`WriteAllText` ohne Lock → bei gleichzeitigem Schreiben/Lesen: `IOException` (abgefangen, aber Setting verloren) oder korrupte JSON. Mindestens ein `lock` um Load/Save.

### #29 — LoggingService erstellt bei jedem `Log()` ein `new SettingsService()` → Verzeichnis-Anlage pro Log-Zeile
**Datei:** `WPF/FluxDB/Services/LoggingService.cs:49-60`

`GetMaxBufferLines()` instanziiert `SettingsService` neu — dessen Konstruktor prüft/erstellt das Verzeichnis und `Load()` liest die komplette `settings.json` von Disk — **bei jeder einzelnen Log-Zeile**! Massives I/O im Hot-Path des Loggings (das überall aufgerufen wird, inkl. enger Schleifen). Cachen oder DevSetting einmalig lesen.

### #30 — `IndexResult.FilesIndexed` wird in Phase 1 als Zähler missbraucht
**Datei:** `WPF/FluxDB/Services/IndexerService.cs:53-59`

Erst `FilesIndexed = Count()`, dann `TotalFiles = FilesIndexed; FilesIndexed = 0;` — funktioniert, ist aber verwirrend und fehleranfällig. Wichtiger: Phase 1 enumeriert das komplette Dateisystem **zweimal** (einmal zum Zählen, einmal zum Indizieren) — verdoppelt die I/O-Zeit bei großen Bäumen. `TotalFiles` könnte man schrittweise hochzählen (progressiv) oder den Count weglassen.

### #31 — Progress-Division durch Null bei leerem Ordner
**Datei:** `WPF/FluxDB/Services/IndexerService.cs:130-140`

Wenn `result.TotalFiles == 0` (leerer Ordner) und trotzdem `processed % 100 == 0` erreicht wird (passiert nicht, da keine Dateien), ok — aber `processed == result.TotalFiles` bei 0==0 triggert `(double)0/0` → `NaN` wird an `progressBar.Value` zugewiesen → `ArgumentException` in WPF ProgressBar! Tatsächlich: die `foreach` läuft bei 0 Dateien gar nicht, also sicher. Aber wenn nur übersprungene (zu lange) Pfade existieren, kann `processed > 0` bei `TotalFiles == 0` nicht vorkommen, da TotalFiles aus derselben Enumeration stammt. Grenzfall: Verzeichnis ändert sich zwischen Phase 1 und 2 (Dateien gelöscht) → `TotalFiles` kleiner als `processed` → `Percentage > 100` → ProgressBar wirft `ArgumentException` ("Value must be >= Minimum and <= Maximum"). **Crash bei parallelen FS-Änderungen.**

**Fix:** `Math.Min(processed, TotalFiles)` und/oder `Percentage = Math.Min(100, ...)`.

### #32 — `MapFileEntry` Spaltenindizes hart codiert & `f.*` Fragilität
**Datei:** `WPF/FluxDB/Services/DatabaseService.cs:163-191`

`SELECT f.*, n.note, ...` mit harten Indizes 0..10. Wenn das Schema der `files`-Tabelle jemals eine Spalte bekommt (Migration), rutschen alle Indizes → falsche Daten. Robust: `GetOrdinal("path")` etc. Der `SelectMany(t => t.Split(new[]{"\\0"}))` in Zeile 182 ist ein Überbleibsel (splittet auf Literal "\0" Backslash-Zero — ist schon durch den echten `\0`-Split erledigt, doppelt gemoppelt, harmlos aber toter Code).

### #33 — Export schreibt `CreatedAt`/`ModifiedAt` als DateTime, Import parsed mit TryParse
**Datei:** `WPF/FluxDB/Services/ExportService.cs:64-65`, `WPF/FluxDB/Services/ImportService.cs:47-48`

`jsonWriter.WriteValue(file.CreatedAt)` schreibt ISO8601 mit `DateTime`-Serialisierung von Newtonsoft (inkl. möglicher lokaler Offset). Import: `DateTime.TryParse(file.CreatedAt, ...)` — kulturabhängig; auf einem System mit anderer Culture kann das fehlschlagen oder falsche Zeiten liefern (z. B. "01/02/2026" Mehrdeutigkeit, wenn der Serializer doch mal lokal formatiert). Besser `"o"`-Format explizit beim Export.
